# Windows process lifecycle notifications

Platform.Windows owns native message decoding and the hidden top-level lifecycle window. Host owns the shared Stop transaction, persistence, Renderer retirement and final exit code. This module does not launch Renderers, change Assignment, send Renderer IPC, restart Explorer, or initiate Windows shutdown/logoff.

`WindowsProcessExitMonitor` uses a separate STA dispatcher, not the Surface dispatcher. A bounded native exit callback may wait for Host cleanup without blocking the thread needed to destroy Surface HWNDs. The window is created before Host startup restore; Program owns it and releases it only after shared Runtime Stop. Console control callbacks and window messages share one cleanup task.

`WindowsProcessShutdownOrder` explicitly configures each participating process: Host uses `0x281`, Renderer uses `0x280`. Windows shuts higher levels down first and otherwise starts processes at `0x280`, so equal defaults do not express the Host-to-Renderer dependency. See [SetProcessShutdownParameters](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessshutdownparameters). This is process-local shutdown ordering, not CPU priority, registry policy, a service, or a global OS setting. Both values stay in the application range; flags remain zero (no SHUTDOWN_NORETRY). The lease reads back the applied value, rejects setup/readback failure before the process reports readiness, and restores its original values once normal ownership ends. Production Program and the explicit active session-end observer hold the Host lease through Runtime/native cleanup; RendererChildProbe sets its Renderer lease before the protocol handshake. This requests ordering but does not guarantee survival against force termination or prove what caused an earlier Renderer exit.

`WM_QUERYENDSESSION` returns TRUE immediately without stopping. `WM_ENDSESSION(FALSE)` is a cancelled query and must not stop the Host. Confirmed `WM_ENDSESSION(TRUE)` and owned `WM_CLOSE` request Stop. ENDSESSION flags are bitmasks; shutdown and restart cannot be distinguished when flags are zero. These semantics follow [WM_QUERYENDSESSION](https://learn.microsoft.com/en-us/windows/win32/shutdown/wm-queryendsession) and [WM_ENDSESSION](https://learn.microsoft.com/en-us/windows/win32/shutdown/wm-endsession).

Native waiting is capped at four seconds and never cancels shared cleanup. A timeout is recorded, not called graceful success; Windows may terminate a process before its ordinary Renderer retirement budget finishes. No shutdown blocking API or promise of unlimited time is introduced. Console close and session controls use [SetConsoleCtrlHandler](https://learn.microsoft.com/en-us/windows/console/setconsolectrlhandler), while Ctrl+C/Break remain routed through Program's managed console callback. User32-loaded applications still require the hidden window for session-end delivery.

An optional Host-owned observation writer now runs after cleanup is observed and before the shared native operation completes. The same four-second budget reserves at most 500 ms (one quarter for smaller budgets) for writing; it is not an extra shutdown allowance. Cleanup and persistence have separate outcomes. One first-request operation owns the deadline and observation; duplicate signals cannot rewrite its reason, retry its write, extend its budget or erase a timeout. Even synchronously blocking callbacks run off the native thread. Expiry cancels only the observation write/wait, never shared Runtime cleanup. A non-cooperative writer cannot be forcibly stopped, and no hard storage-latency guarantee is made.

Platform emits only a typed cleanup observation; Host correlates and persists `host-native-exit-receipt.json` with the separate Runtime receipt. `NativeCallbackCleanupObserved` means the native handling path observed cleanup and attempted persistence, not that the callback has returned, Main has completed, or the OS exit code was observed. Those latter claims remain explicitly false in the record. A file cannot independently attest its own eventual return-to-Windows timing. Controlled process checks still verify actual exit code, window disposal and persistence; new real-session samples validate the narrower correlated callback evidence. Historical stdout-only samples do not acquire the new contract retroactively.

The internal readiness message is read-only and supports owned-process diagnostics; it is not Renderer IPC or a public compatibility contract. No native HWND/PID becomes a persisted compatibility identity. Monitor tests send messages only to owned windows; the process harness sends only to the child Host it starts. Controlled message injection is not an actual Windows logout/shutdown sample.
